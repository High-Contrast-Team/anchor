# WCAG 2.1 AA audit, 27 September 2026

The public Anchor website does **not** fully meet WCAG 2.1 Level AA. Two primary buttons render with a 1:1 contrast ratio (WCAG 1.4.3). The repo gate still exits 0, because axe-core files those buttons as incomplete rather than as violations.

This note is the handoff for a later fix. No styles were changed in this pass.

## How this was run

- Tree audited: `39c5debea20dd449341e1c706ce1b59b3929c1f7`. `origin/main` at `e2edac5945bf0c6f0b1db9345ef67f7ebab57d4c` does not change `apps/web`.
- Build: `astro build --root apps/web`, then `astro preview` at `http://127.0.0.1:4321` (production HTML, no dev toolbar).
- Engine: axe-core 4.13.0, tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`.
- Gate: `node apps/web/scripts/a11y-check.mjs` (`pnpm a11y:web`). Result: **0 violations**, exit 0.
- Extra pass: the same 10 routes, consent banner open and dismissed, desktop 1280×720 and mobile 390×844. 40 runs, **0 axe violations**. Raw output: [2026-09-27-wcag-2.1-aa.json](./2026-09-27-wcag-2.1-aa.json).
- Contrast was then measured from computed styles in Chromium. That measurement is what catches the failure below.

Routes in the gate: `/`, `/how-it-works`, `/app`, `/family`, `/my-data`, `/privacy`, `/terms`, `/cookies`, `/sitemap`, and an unknown URL that renders the 404 page.

`/designs/ink`, `/designs/linen`, `/designs/mist`, `/designs/quiet`, and `/designs/slate` are built and reachable, but they are not on the public sitemap and they are not in the gate. They were not audited.

## Failure to fix

**WCAG 1.4.3 Contrast (Minimum), Level AA.** Normal text needs at least 4.5:1. These controls are 15px, so they count as normal text.

| Page | Control | Computed color | Computed background | Ratio |
| --- | --- | --- | --- | --- |
| `/how-it-works` | `Get started` (`a.btn.btn-primary`) | `rgb(68, 61, 255)` | `rgb(68, 61, 255)` | **1:1** |
| 404 | `Back to Anchor` (`a.btn.btn-primary`) | `rgb(68, 61, 255)` | `rgb(68, 61, 255)` | **1:1** |

Source:

- `apps/web/src/pages/how-it-works.astro` (the `Get started` link inside `article.prose`)
- `apps/web/src/pages/404.astro` (the `Back to Anchor` link inside `article.prose`)
- `apps/web/src/styles/tokens.css`

### Why

`.btn-primary` sets the label to the background color on a primary fill:

```css
.btn-primary,
.slate-btn-primary {
  background: hsl(var(--primary));
  color: hsl(var(--background));
}
```

`.prose a` is more specific (one class plus one element, against one class), so it wins and paints the label the same purple as the fill:

```css
.prose a {
  color: hsl(var(--primary));
  font-weight: 600;
}
```

Buttons that are not inside `.prose` are fine. The home page `Start Remembering Together` links and the consent `Accept` button are light text on primary, about **6.06:1**.

The same override hits the secondary links on those two pages (`Try the scripted demo`, `Open the demo`). Their text becomes primary on the accent fill, about **4.66:1**. That still clears 4.5:1, with little room to spare. The intended secondary color (near-black on accent) is about **15.18:1**. One specificity fix covers both.

High contrast mode (`html.a11y-contrast`) does not escape this. `.prose a` still wins, so the label stays primary on a primary fill.

axe-core reports the 1:1 buttons under `incomplete` / `color-contrast` ("Element has a 1:1 contrast ratio with the background"), so `apps/web/scripts/a11y-check.mjs` ignores them. After the CSS fix, those incomplete results should disappear. If the gate should catch this class of miss on its own, teach it to fail on a 1:1 `color-contrast` incomplete, or assert the computed ratio of `.prose a.btn-primary`.

### Suggested change

Keep button colors ahead of the prose link color. Something with equal or higher specificity than `.prose a`:

```css
.prose a.btn-primary {
  color: hsl(var(--background));
}

.prose a.btn-secondary,
.prose a.btn-quiet {
  color: hsl(var(--text));
}
```

Repeat the hover colors already set on `.btn-primary:hover` and `.btn-secondary:hover`, or the hover rule will lose to `.prose a:hover` the same way. Do not hard-code hex in the component. Use the existing tokens.

## Incomplete results that are not failures

axe also marked `color-contrast` incomplete where the fixed consent banner covers part of the page (`#consent-title`, `#consent-body`, and sometimes a button sitting under the banner). The message is that the background could not be sampled because another element overlaps it. That is a measurement limit, not a confirmed 1.4.3 failure. The banner's own `Accept` button measures 6.06:1.

## What already meets the checks

- axe WCAG 2.1 A and AA: 0 violations on 10 public routes, both consent states, desktop and mobile.
- `html lang="en"`, a single `h1` on the pages sampled, and heading levels on `/how-it-works` and `/privacy` do not skip.
- Skip link (`Skip to content` to `#main`), primary nav, footer nav, and the page buttons are in tab order on `/how-it-works`. Keyboard focus shows a 2px solid primary outline with a 3px offset (`:focus-visible` in `tokens.css`).
- The wordmark image is `alt=""` beside the visible word "Anchor", so it is decorative.
- Footer accessibility note at 60% text opacity on the page background measures about **5.44:1** at 15px.
- In-prose links (primary on the page background) measure about **6.06:1**.

## Not covered

Full keyboard traversal of `/app`, `/family`, and `/my-data` (those pages have forms and dialogs). Text resized to 200% (1.4.4) and reflow at 320px (1.4.10). Screen reader announcements. Third-party Telegram and messenger login windows, which the footer already calls out as outside this site. The five `/designs/*` pages.
